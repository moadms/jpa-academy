La Métaphore Ultime

Comment fonctionne TP 5 ? Imaginez un Restaurant 5 Étoiles ! 🍽️

1. Le Client (Presentation)

PresentationSpringHibernate.java

Il passe la commande ("Je veux ajouter un MacBook Pro et afficher son prix"). Il ne sait pas comment la cuisine fonctionne, il parle juste au serveur.

2. Le Maître d'Hôtel (@Service)

ProduitServiceImpl.java

Il applique les règles métier. C'est lui qui gère la Transaction (@Transactional) : si le plat brûle ou si un ingrédient manque, il annule tout (Rollback) !

3. Le Cuisinier (@Repository / DAO)

ProduitDaoImpl.java

Il sait manipuler les ustensiles (Hibernate SessionFactory). Il va chercher les ingrédients bruts dans le frigo et les transforme.

4. Le Frigo (Base de Données)

H2 Database / MySQL

Là où sont stockées les données physiques dans des tables de disques ou mémoire RAM (tables produits).

Le Déclic Pédagogique

Pourquoi avoir besoin des DEUX ensemble ?

Dans le TP 4, nous utilisions Hibernate seul. C'était fastidieux : nous devions ouvrir manuellement la Session, faire tx = session.beginTransaction(), puis tx.commit(), et attraper chaque exception pour faire tx.rollback(). C'était ce qu'on appelle du code boilerplate (répétitif et source d'erreurs).

Hibernate seul : Gestion manuelle des sessions, fermeture risquant les fuites de mémoire (memory leak), couplage fort avec l'API Hibernate.

Spring + Hibernate (TP 5) : Spring gère la fabrique d'usine (LocalSessionFactoryBean), injecte les dépendances automatiquement (@Autowired) et pilote les transactions déclarativement avec un simple @Transactional !

Au Microscope

Toutes les Annotations du TP 5 Décortiquées

Chaque annotation a un super-pouvoir bien précis. Les voici expliquées une par une.

@Configuration Couche : Configuration
SpringHibernateConfig.java

💡 Expliqué à un débutant

C'est la recette de cuisine ou le plan d'architecte de Spring ! En mettant @Configuration au-dessus d'une classe, vous dites à Spring : "Attention, cette classe ne contient pas de données clients, elle contient les instructions pour construire et brancher toutes les pièces du moteur (les Beans) !"

⚙️ Sous le capot (JVM)

Spring génère un proxy CGLIB autour de cette classe pour garantir que chaque méthode annotée @Bean n'est exécutée qu'une seule fois (principe du Singleton dans le conteneur).

// Déclare la classe comme source de définitions de beans @Configuration @ComponentScan(basePackages = {"dao", "service"}) @EnableTransactionManagement public class SpringHibernateConfig { // Contient les méthodes @Bean }
@Bean Couche : Fabrique d'objets
SpringHibernateConfig.java

💡 Expliqué à un débutant

Un @Bean est un objet fabriqué et gardé précieusement dans le coffre-fort de Spring (le Conteneur IoC). Quand vous appliquez @Bean sur une méthode, vous dites à Spring : "Exécute cette méthode, prends l'objet qu'elle retourne, et garde-le en mémoire. Dès que quelqu'un en a besoin, donne-lui !"

Question piège Prof : Pourquoi utiliser @Bean au lieu de @Component ?
➔ Réponse : Pour les classes de bibliothèques externes (comme DataSource ou LocalSessionFactoryBean) dont nous n'avons pas le code source pour y ajouter @Component !
@Bean public DataSource dataSource() { DriverManagerDataSource ds = new DriverManagerDataSource(); ds.setDriverClassName("org.h2.Driver"); ds.setUrl("jdbc:h2:mem:spring_hibernate_db;DB_CLOSE_DELAY=-1"); ds.setUsername("sa"); ds.setPassword(""); return ds; // Spring stocke ce DataSource ! }
@EnableTransactionManagement @Transactional Élément Star du TP 5
Config & Service

💡 Expliqué à un débutant

Imaginez que vous faites un virement bancaire de 100 DH :
1. On retire 100 DH de votre compte.
2. Une coupure de courant arrive avant de les donner au destinataire !
Grâce à @Transactional, l'opération est ATOMIQUE (Tout ou Rien) : si un problème survient au milieu, tout est annulé (Rollback) et vous ne perdez pas votre argent. Si tout s'est bien passé, la transaction est validée (Commit).

⚙️ Le rôle de readOnly = true

Sur les méthodes de consultation (comme consulterTousProduits()), on met @Transactional(readOnly = true). Cela signale à Hibernate d'optimiser la mémoire en désactivant le Dirty Checking (inutile de vérifier si les objets ont changé puisqu'on ne fait que lire !).

@Service @Transactional // Toutes les méthodes sont transactionnelles public class ProduitServiceImpl implements IProduitService { @Autowired private IProduitDao produitDao; public Produit ajouterProduit(Produit p) { // Si une RuntimeException survient -> ROLLBACK automatique return produitDao.save(p); } @Transactional(readOnly = true) // Optimisation lecture public List<Produit> consulterTousProduits() { return produitDao.findAll(); } }
@Entity & JPA Mapping Couche : Domaine / Entités
Produit.java

💡 Expliqué à un débutant

Une classe Java vit dans la mémoire RAM sous forme d'objet. Une base de données stocke des lignes dans des tables SQL. Ces annotations sont le passeport de traduction (ORM) :

  • @Entity : Dit à Hibernate "Transforme cette classe en table SQL".
  • @Table(name="produits") : Nom personnalisé de la table.
  • @Id : La clé primaire unique de chaque produit.
  • @GeneratedValue(strategy = GenerationType.IDENTITY) : Auto-incrémentation (1, 2, 3...) gérée par la base.
  • @Column(name="designation", length=150) : Spécifie la colonne SQL et sa taille maximale.
@Entity @Table(name = "produits") public class Produit implements Serializable { @Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id; @Column(name = "designation", nullable = false, length = 150) private String designation; @Column(name = "prix", nullable = false) private double prix; private int quantite; }
@Repository & @Autowired Couche : DAO (Accès aux Données)
ProduitDaoImpl.java

💡 Expliqué à un débutant

@Repository est le badge qui indique à Spring : "Cette classe parle directement avec la base de données !"
Son super-pouvoir caché : elle intercepte les vilaines exceptions SQL spécifiques (comme SQLException) et les traduit automatiquement en exceptions Spring compréhensibles (DataAccessException).

@Autowired est l'aimant d'injection : il demande à Spring de fournir automatiquement l'instance de SessionFactory déjà configurée !

@Repository public class ProduitDaoImpl implements IProduitDao { @Autowired private SessionFactory sessionFactory; private Session getSession() { // Utilise la session courante liée à la transaction @Transactional return sessionFactory.getCurrentSession(); } public Produit save(Produit p) { getSession().persist(p); return p; } }
Le Secret d'Hibernate

Les 4 États d'une Entité (Cycle de Vie)

Tous les professeurs adorent interroger les étudiants sur ce schéma lors des soutenances !

ÉTAT 1

Transient (Nouveau)

Créé avec un simple new Produit().

Pas d'ID en base
Inconnu de la Session
Existe juste dans la RAM
ÉTAT 2 (STAR)

Persistent (Managé)

Après session.persist(p) ou session.get(id).

Possède un ID valide
Rattaché à la Session
Synchronisé automatiquement (Dirty Checking)
ÉTAT 3

Detached (Détaché)

Après la fermeture de la transaction ou session.close().

Possède toujours son ID
Session fermée
Tout getLazy() lance une LazyInitializationException !
ÉTAT 4

Removed (Supprimé)

Après appel à session.remove(p).

Marqué pour suppression SQL
DELETE exécuté au commit
Antisèche Examen & Recrutement

Les 5 Questions Pièges du Professeur (et leurs Réponses !) 🎯

Si votre professeur vous pose ces questions lors du test ou de l'oral, voici les réponses en or.

1 Quelle est la différence entre SessionFactory et Session ?

Réponse de l'expert :
• SessionFactory est un objet très lourd, thread-safe, créé une seule fois au démarrage de l'application. Elle contient les métadonnées de toutes les entités et le pool de connexions.
• Session est un objet très léger, non thread-safe, à courte durée de vie (dure le temps d'une requête ou d'une transaction). Elle représente une connexion physique ouverte avec la base.

2 Pourquoi Session.persist() et non Session.save() ?

Réponse de l'expert :
save() est une méthode historique propre à Hibernate qui retourne l'ID immédiatement. persist() est la méthode standard officielle de la spécification **JPA**. En utilisant persist(), notre code respecte le standard JPA et peut être porté facilement sans dépendance forte à Hibernate.

3 Pourquoi @Transactional doit être sur la couche Service et non DAO ?

Réponse de l'expert :
Parce qu'une opération métier (Service) implique souvent plusieurs appels DAO (ex: débiter un compte dans CompteDao + créditer un autre compte dans CompteDao + ajouter un log dans LogDao). La transaction doit englober l'ensemble de l'action métier pour que si le log échoue, le débit soit également annulé !

4 Le piège du "Self-Invocation" avec @Transactional

Réponse de l'expert :
Si dans la classe ProduitServiceImpl, la méthode A() (non transactionnelle) appelle this.B() (annotée @Transactional), la transaction ne démarrera PAS ! Pourquoi ? Parce que Spring utilise des Proxies. En faisant un appel interne this.B(), on court-circuite le proxy Spring !
