TP 1 • Fondations & Bootstrap 📁 Repositoire : TP1-JPA-Hibernate

Introduction à Maven, Hibernate & H2 In-Memory

Architecture fondamentale, bootstrap JPA et gestion des transactions

🛑 Le Problème Initial (Pourquoi ce TP existe) :

En JDBC pur, le développeur devait écrire des requêtes SQL manuelles en concaténant des chaînes (risque d'injection SQL), mapper chaque colonne manuellement via ResultSet.getXXX(), gérer manuellement l'ouverture et la fermeture des connexions, et gérer les transactions au niveau de la connexion physique.

✅ La Solution & Innovation Apportée :

JPA abstrait la base de données. On manipule des objets Java (POJOs). Hibernate génère le DDL (CREATE TABLE) et le DML (INSERT, SELECT) de manière transparente. H2 en mode mémoire (jdbc:h2:mem:...) permet d'exécuter des tests ultrarapides sans installer de serveur MySQL/PostgreSQL.

🔬 Ce qu'il faut absolument connaître dans ce TP :

pom.xml & Dépendances Clés

hibernate-core (moteur d'exécution ORM), h2 (base embarquée en RAM), junit-jupiter (tests unitaires) et slf4j/logback (journalisation SQL).

<dependency>
  <groupId>org.hibernate</groupId>
  <artifactId>hibernate-core</artifactId>
  <version>5.6.5.Final</version>
</dependency>
<dependency>
  <groupId>com.h2database</groupId>
  <artifactId>h2</artifactId>
  <version>2.1.214</version>
  <scope>runtime</scope>
</dependency>

META-INF/persistence.xml

Définit la 'persistence-unit' (unité de persistance). En mode Java SE standalone, le transaction-type est impérativement RESOURCE_LOCAL. Les propriétés configurent le pilote H2, le mode hbm2ddl (update/create-drop) et l'affichage des requêtes SQL (show_sql, format_sql).

<persistence-unit name="gestion-reservations" transaction-type="RESOURCE_LOCAL">
  <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
  <properties>
    <property name="javax.persistence.jdbc.url" value="jdbc:h2:mem:reservations_db;DB_CLOSE_DELAY=-1"/>
    <property name="javax.persistence.jdbc.driver" value="org.h2.Driver"/>
    <property name="hibernate.dialect" value="org.hibernate.dialect.H2Dialect"/>
    <property name="hibernate.hbm2ddl.auto" value="update"/>
    <property name="hibernate.show_sql" value="true"/>
    <property name="hibernate.format_sql" value="true"/>
  </properties>
</persistence-unit>

EntityManagerFactory vs EntityManager

EntityManagerFactory est un composant lourd (Singleton applicatif, thread-safe, coûteux à initialiser car analyse tout le métamodèle). L'EntityManager est un composant léger (non thread-safe, représente une session d'accès aux données, créé par requête ou par thread, et doit être fermé après usage).

// Singleton Pattern recommandé en Java SE
public class HibernateUtil {
  private static final EntityManagerFactory emf = 
      Persistence.createEntityManagerFactory("gestion-reservations");
  public static EntityManager getEntityManager() {
    return emf.createEntityManager();
  }
  public static void close() {
    emf.close();
  }
}

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

Monsieur, l'EntityManagerFactory est un objet lourd dont la création nécessite l'analyse du classpath, la lecture du persistence.xml, la compilation du métamodèle des entités, la validation des schémas et l'initialisation du pool de connexions. Ce processus prend entre 1 et 3 secondes et consomme plusieurs dizaines de mégaoctets de RAM. S'il est instancié à chaque appel de DAO, l'application subit une dégradation dramatique de performance et finit en OutOfMemoryError. En revanche, l'EntityManager est un objet léger, non thread-safe, conçu pour être créé et fermé fréquemment.

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

En mode RESOURCE_LOCAL, si em.persist() est appelé hors transaction, soit Hibernate lève une TransactionRequiredException (dans les versions strictes), soit l'entité est placée temporairement dans le contexte de persistance L1 mais aucun 'flush' SQL n'est jamais déclenché vers la base de données. À la fermeture de l'EntityManager, les données en mémoire sont perdues et rien n'est persisté en table. Toute opération d'écriture (persist, merge, remove) requiert impérativement un em.getTransaction().begin() et commit().

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

JPA (Jakarta Persistence API) est une spécification officielle, c'est-à-dire un ensemble d'interfaces Java (EntityManager, EntityManagerFactory, EntityTransaction) et d'annotations (@Entity, @Table, @Id) définies par un standard. Hibernate est l'implémentation concrète (le framework ORM) qui implémente ces interfaces avec son moteur interne (Hibernate Core, Session, SessionFactory). On programme contre les interfaces JPA pour garantir la portabilité du code.

TP 2 • Cycle de Vie & Mapping 📁 Repositoire : TP2-JPA-Hibernate

Entités JPA, Clés Primaires, Annotations & Cycle de Vie

États du Contexte de Persistance, Dirty Checking et génération d'identifiants

🛑 Le Problème Initial (Pourquoi ce TP existe) :

Dans les anciens modèles, les clés primaires étaient gérées manuellement ou via des triggers complexes. De plus, modifier un objet obligeait à appeler explicitement une méthode update() ou une requête UPDATE SQL avec le risque d'oublier des colonnes ou de créer des désynchronisations d'états.

✅ La Solution & Innovation Apportée :

JPA introduit le 'Contexte de Persistance' et le mécanisme de 'Dirty Checking' (vérification de salissure). Dès qu'un objet est MANAGED, Hibernate conserve un instantané (snapshot) de ses valeurs d'origine. Au commit de la transaction, Hibernate compare l'état courant avec le snapshot et génère automatiquement l'UPDATE SQL pour les champs modifiés, sans aucun appel explicite à une méthode d'update !

🔬 Ce qu'il faut absolument connaître dans ce TP :

Les 4 Stratégies @GeneratedValue

IDENTITY (utilise auto-increment SQL, empêche le batch insert d'Hibernate car l'ID est connu seulement après l'INSERT), SEQUENCE (utilise une séquence DB, optimal pour le batching et les bases comme Oracle/PostgreSQL), TABLE (table dédiée de compteurs, portable mais lente), AUTO (choix automatique par le dialecte).

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

Les 4 États du Cycle de Vie JPA

1. TRANSIENT / NEW : new Entite(), pas d'ID, inconnu d'Hibernate. 2. MANAGED : em.persist() ou em.find(), rattaché au contexte de persistance L1, surveillé par le Dirty Checking. 3. DETACHED : em.detach() ou après em.close(), possède un ID mais n'est plus surveillé. 4. REMOVED : em.remove(), marqué pour suppression SQL au flush.

Utilisateur u = new Utilisateur("Moad"); // TRANSIENT
em.persist(u);                           // MANAGED
em.detach(u);                            // DETACHED
Utilisateur managed = em.merge(u);       // 'managed' est MANAGED, 'u' reste DETACHED !
em.remove(managed);                      // REMOVED

Le Piège de equals() et hashCode()

Surcharger equals/hashCode uniquement sur l'ID généré est un piège majeur : avant le persist, id vaut null. Si l'objet est inséré dans un HashSet puis persisté, son hashCode change et l'objet devient introuvable dans le Set ! La bonne pratique est d'utiliser une 'Clé Métier' (Business Key stable, ex: email, codeSalle).

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Utilisateur)) return false;
    Utilisateur that = (Utilisateur) o;
    return Objects.equals(email, that.email); // Clé métier stable
}

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

Monsieur, le Dirty Checking est le mécanisme automatique de détection des modifications d'Hibernate. Lorsqu'une entité entre dans le Contexte de Persistance (via find() ou persist()), Hibernate stocke en mémoire une copie miroir appelée 'snapshot'. Lors du flush (à la fin de la transaction), Hibernate compare chaque champ de l'entité active avec ce snapshot. Si une différence est détectée, Hibernate génère automatiquement la requête SQL UPDATE correspondante. C'est pourquoi il n'existe pas de méthode 'em.update()' en JPA.

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

C'est impérativement la valeur de retour de la méthode merge() qui devient MANAGED ! L'objet passé en paramètre reste à l'état DETACHED. Si on continue à modifier l'instance passée en paramètre sans réassigner 'u = em.merge(u)', ces nouvelles modifications ne seront jamais enregistrées en base.

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

Parce qu'avec la stratégie IDENTITY, l'identifiant n'est attribué par le moteur de base de données qu'au moment précis où la ligne est insérée physiquement. Hibernate doit donc exécuter l'INSERT immédiatement lors de l'appel em.persist() pour récupérer l'ID généré, brisant ainsi la mise en file d'attente nécessaire au batching. Avec GenerationType.SEQUENCE, Hibernate peut pré-allouer une plage d'IDs à l'avance et regrouper tous les INSERTs en un seul envoi JDBC.

TP 3 • Associations & Cascades 📁 Repositoire : TP3-JPA-Hibernate

Associations Fondamentales & Relations Complexes

OneToMany, ManyToOne, ManyToMany, mappedBy et Suppression Orpheline

🛑 Le Problème Initial (Pourquoi ce TP existe) :

En base relationnelle, une relation OneToMany se traduit par une clé étrangère stockée dans la table fille (plusieurs). En Java, l'objet parent possède une List. Si on ne met à jour que la liste Java sans mettre à jour la clé étrangère sur l'objet enfant, Hibernate n'écrit rien en base de données !

✅ La Solution & Innovation Apportée :

Définition rigoureuse du propriétaire avec @JoinColumn et du côté inverse avec mappedBy. Création systématique de méthodes helpers synchronisées (addReservation/removeReservation) qui garantissent que les deux côtés de la relation en RAM sont toujours cohérents.

🔬 Ce qu'il faut absolument connaître dans ce TP :

Le Propriétaire de l'Association & mappedBy

Le côté propriétaire est TOUJOURS celui qui porte la clé étrangère en base (généralement le @ManyToOne avec @JoinColumn). Le côté inverse porte mappedBy='nomDuChampChezLeProprietaire'. Pour Hibernate, mappedBy est une vue miroir en lecture seule. Seul le côté propriétaire déclenche les écritures SQL !

// Côté Inverse (Vue lecture seule pour Hibernate)
@OneToMany(mappedBy = "salle", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Reservation> reservations = new ArrayList<>();

// Côté Propriétaire (Porte la clé étrangère physique salle_id)
@ManyToOne
@JoinColumn(name = "salle_id", nullable = false)
private Salle salle;

Méthodes Helpers de Synchronisation

Obligatoires pour maintenir la cohérence en mémoire Java des deux côtés de l'association bidirectionnelle.

public void addReservation(Reservation r) {
    reservations.add(r);
    r.setSalle(this); // MAJ du côté propriétaire !
}
public void removeReservation(Reservation r) {
    reservations.remove(r);
    r.setSalle(null); // Détachement
}

CascadeType.REMOVE vs orphanRemoval = true

CascadeType.REMOVE : Si le parent est supprimé (em.remove(parent)), tous ses enfants sont supprimés en cascade. orphanRemoval = true : Si un enfant est retiré de la collection Java du parent (parent.getEnfants().remove(e)), Hibernate génère un DELETE SQL pour supprimer physiquement cet enfant orphelin de la base !

@OneToMany(mappedBy = "salle", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Reservation> reservations = new ArrayList<>();

Piège Fatal : CascadeType.REMOVE sur @ManyToMany

Ne JAMAIS mettre CascadeType.REMOVE sur une relation @ManyToMany (ex: Salle <-> Equipement). Sinon, en supprimant une Salle, vous supprimez physiquement les Projecteurs et Écrans partagés par d'autres salles !

// BONNE PRATIQUE @ManyToMany : AUCUN CascadeType.REMOVE !
@ManyToMany
@JoinTable(name = "salle_equipements",
    joinColumns = @JoinColumn(name = "salle_id"),
    inverseJoinColumns = @JoinColumn(name = "equipement_id"))
private Set<Equipement> equipements = new HashSet<>();

Cliquez pour révéler la réponse type
👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

Monsieur, la colonne salle_id de la réservation restera NULL (ou lèvera une contrainte d'intégrité NOT NULL) et le lien ne sera pas créé en base ! La collection portée par la Salle a l'attribut mappedBy, ce qui signifie qu'elle est ignorée par Hibernate lors de la génération des requêtes INSERT/UPDATE SQL. Seul le côté propriétaire (Reservation.salle annoté @ManyToOne) est pris en compte pour renseigner la clé étrangère.

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

CascadeType.REMOVE ne s'active QUE lorsque l'entité parente elle-même fait l'objet d'un em.remove(parent). Les enfants sont alors supprimés en chaîne. En revanche, orphanRemoval=true s'active lorsque l'enfant est simplement détaché de sa collection parente en mémoire (ex: salle.getReservations().remove(r)). Hibernate détecte cet orphelin déréférencé et exécute un DELETE SQL sur l'enfant, même si la salle parente continue d'exister.

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

Avec une List, si on ajoute ou supprime un élément, Hibernate ne peut pas garantir l'unicité des paires sans vider entièrement la table de jointure pour la salle concernée (DELETE FROM salle_equipements WHERE salle_id = ?) puis réinsérer toutes les lignes une par une ! Avec un Set, Hibernate sait identifier précisément la ligne à supprimer ou à insérer, ce qui évite de réécrire toute la table de jointure.

@Test
void testOrphanRemoval() {
    EntityManager em = emf.createEntityManager();
    em.getTransaction().begin();
    Salle salle = em.find(Salle.class, 1L);
    Reservation r = salle.getReservations().get(0);
    Long resId = r.getId();
    salle.removeReservation(r); // Retrait de la collection via helper
    em.getTransaction().commit();

}
TP 4 • Héritage & Polymorphisme 📁 Repositoire : TP4-Hibernate-Inheritance

Héritage Objet-Relationnel avec Hibernate

SINGLE_TABLE, JOINED, TABLE_PER_CLASS et @MappedSuperclass

🛑 Le Problème Initial (Pourquoi ce TP existe) :

Comment stocker des sous-classes ayant à la fois des attributs communs (nom, salaire) et des attributs spécifiques (langagePrincipal pour Developpeur, prime pour Manager) sans briser les contraintes de clés primaires ni ruiner les performances de lecture ?

✅ La Solution & Innovation Apportée :

JPA propose l'annotation @Inheritance(strategy = InheritanceType....). Chaque stratégie offre un compromis différent entre normalisation relationnelle et vitesse d'exécution SQL.

🔬 Ce qu'il faut absolument connaître dans ce TP :

1. SINGLE_TABLE (Stratégie par défaut)

Une seule table physique regroupe toute la hiérarchie. Une colonne de discrimination (@DiscriminatorColumn) stocke le type ('DEV', 'MGR'). Avantage : 0 jointure, lecture ultra-rapide. Inconvénient : Les colonnes spécifiques des sous-classes doivent obligatoirement être NULLABLE (impossible de mettre NOT NULL).

@Entity
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "type_employe", discriminatorType = DiscriminatorType.STRING)
public abstract class Employe { ... }

@Entity
@DiscriminatorValue("DEV")
public class Developpeur extends Employe { ... }

2. JOINED (Héritage Normalisé)

Une table pour la classe mère + une table pour chaque sous-classe. La table fille utilise sa clé primaire comme clé étrangère vers la table mère. Avantage : Schéma relationnel 3NF propre, contraintes NOT NULL possibles sur les champs spécifiques. Inconvénient : Requêtes polymorphiques nécessitent des JOIN coûteux.

@Entity
@Inheritance(strategy = InheritanceType.JOINED)
public abstract class Employe { ... }

@Entity
@Table(name = "developpeurs")
public class Developpeur extends Employe { ... }

3. TABLE_PER_CLASS (Tables Indépendantes)

Chaque classe concrète a sa propre table contenant tous les champs (hérités + spécifiques). Inconvénient majeur : Les requêtes polymorphiques ('FROM Employe') génèrent des requêtes UNION SQL très lentes.

@Entity
@Inheritance(strategy = InheritanceType.TABLE_PER_CLASS)
public abstract class Employe { ... }

4. @MappedSuperclass (Factorisation d'Attributs)

N'est PAS une entité. Aucune table n'est créée pour elle. Elle sert uniquement à factoriser des champs techniques communs (id, dateCreation, creePar) dans les classes filles. On ne peut pas faire de requête polymorphique dessus.

@MappedSuperclass
public abstract class BaseEntity {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private LocalDateTime dateCreation = LocalDateTime.now();
}

Cliquez pour révéler la réponse type
👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

Monsieur, je choisirais la stratégie JOINED. Dans un contexte bancaire, la règle d'intégrité relationnelle et les contraintes NOT NULL sur les colonnes métier sont non négociables. SINGLE_TABLE nous obligerait à accepter des colonnes NULL sur les attributs spécifiques, ce qui compromet la rigueur du schéma. JOINED offre une normalisation parfaite en troisième forme normale (3NF).

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

Hibernate génère une requête avec des jointures externes : SELECT e.*, d.*, m.* FROM employes e LEFT OUTER JOIN developpeurs d ON e.id = d.id LEFT OUTER JOIN managers m ON e.id = m.id. Hibernate lit les résultats et instancie la classe concrète Developpeur ou Manager selon quelle jointure renvoie des données.

👑 Réponse Parfaite de l'Ingénieur (Format Oral 20/20) :

Parce que @MappedSuperclass n'est pas une entité JPA reconnue dans le métamodèle relationnel. Il n'existe aucune table physique correspondante et aucun discriminateur en base. @MappedSuperclass est uniquement un mécanisme orienté objet Java au moment de la compilation pour hériter des champs, contrairement à @Entity avec @Inheritance qui enregistre la hiérarchie dans le moteur JPA.

TP 5 • Requêtes & Performance 📁 Repositoire : TP5-JPA-Advanced-Queries

Requêtes Avancées JPQL, Pagination & Criteria API

Résolution du piège N+1, filtres dynamiques et optimisation des performances

🛑 Le Problème Initial (Pourquoi ce TP existe) :

En écrivant des requêtes SQL natives codées en dur, on perd la portabilité entre bases (H2, MySQL, Oracle). En paginant les résultats en mémoire Java (ex: list.subList(0, 10)), on charge des millions de lignes en RAM pour n'en afficher que 10, ce qui sature la mémoire du serveur.

✅ La Solution & Innovation Apportée :

JPQL permet de manipuler les classes et propriétés Java en restant indépendant du dialecte SQL sous-jacent. L'API Criteria offre un typage strict (type-safe) évitant les erreurs de syntaxe à l'exécution. Les méthodes de pagination génèrent les clauses LIMIT / OFFSET SQL directement au niveau du serveur de base de données.

🔬 Ce qu'il faut absolument connaître dans ce TP :

JPQL vs SQL & Paramètres Nommés

En JPQL, on écrit 'SELECT s FROM Salle s WHERE s.capacite >= :minCapacite'. On cible la classe Salle et sa propriété capacite, et non la table t_salle ni la colonne col_cap. On utilise setParameter() pour empêcher toute injection SQL.

TypedQuery<Salle> query = em.createQuery(
    "SELECT s FROM Salle s WHERE s.capacite >= :cap ORDER BY s.nom ASC", 
    Salle.class
);
query.setParameter("cap", 20);
List<Salle> resultats = query.getResultList();

Pagination Côté Base de Données

setFirstResult(offset) indique l'indice de départ (0, 10, 20...). setMaxResults(limit) indique le nombre maximum de lignes par page. Hibernate traduit cela en 'LIMIT ? OFFSET ?' sous PostgreSQL/H2 ou 'FETCH NEXT' sous Oracle.

query.setFirstResult((pageNumero - 1) * taillePage); // Ex: (2 - 1) * 10 = 10
query.setMaxResults(taillePage);                      // Ex: 10

Le Sauveur : JOIN FETCH

Un simple JOIN en JPQL filtre les données mais ne charge PAS la relation en mémoire (elle reste LAZY). Le JOIN FETCH force Hibernate à charger l'entité parente ET sa collection d'enfants en UNE SEULE requête SQL avec jointure, éliminant totalement le problème N+1.

// Charge la Salle ET ses équipements en 1 seule requête SQL !
String jpql = "SELECT DISTINCT s FROM Salle s JOIN FETCH s.equipements WHERE s.capacite >= :cap";
List<Salle> salles = em.createQuery(jpql, Salle.class)
    .setParameter("cap", 15)
    .getResultList();

TP 6 • Concurrence & @Version 📁 Repositoire : TP6-Optimistic-Locking-Version

Concurrence, Conflits d'Accès & Verrouillage Optimiste (@Version)

Prévention des 'Lost Updates' et intégrité transactionnelle multi-utilisateurs

🛑 Le Problème Initial (Pourquoi ce TP existe) :

Deux utilisateurs A et B lisent la même réservation (ex: Statut 'EN_ATTENTE'). A modifie le statut en 'CONFIRMÉE' et commit. Une seconde plus tard, B (qui avait lu l'ancien statut) modifie le statut en 'ANNULÉE' et commit. La modification de A est écrasée sans qu'aucun message d'alerte ne soit émis : c'est le 'Lost Update' (Mise à jour perdue).

✅ La Solution & Innovation Apportée :

Ajout d'une colonne de version (@Version private int version;). À chaque mise à jour, Hibernate incrémente automatiquement cette valeur et vérifie dans la clause WHERE que la version n'a pas changé. Si un conflit survient, Hibernate jette une OptimisticLockException.

🔬 Ce qu'il faut absolument connaître dans ce TP :

L'Annotation @Version

S'applique sur un champ de type int, Integer, long, Long ou Timestamp. Hibernate gère ce champ de manière totalement autonome.

@Entity
public class Salle {
    @Id @GeneratedValue
    private Long id;
    private String nom;
    
    @Version
    private int version; // Géré automatiquement par Hibernate
}

La Requête SQL Générée par le Verrou Optimiste

Lors du commit d'une entité modifiée, Hibernate génère l'UPDATE avec un test strict sur la version : UPDATE salle SET nom = ?, version = version + 1 WHERE id = ? AND version = ?. Si 0 ligne est modifiée (car un autre utilisateur a déjà incrémenté la version), Hibernate déclenche OptimisticLockException !

// Requête SQL générée en coulisse :
UPDATE salle 
SET nom = 'Salle Al-Khwarizmi', version = 2 
WHERE id = 1 AND version = 1;

Verrouillage Optimiste vs Pessimiste

Optimiste (@Version) : Ne pose aucun verrou physique en base de données. Idéal pour les systèmes à fort trafic web où les conflits sont rares. Économise les ressources. Pessimiste (PESSIMISTIC_WRITE) : Exécute un 'SELECT ... FOR UPDATE' qui bloque physiquement la ligne au niveau de la base tant que la transaction est ouverte. À réserver aux opérations critiques (débit bancaire, places de concert limitées).

// Verrouillage Pessimiste explicite :
Salle s = em.find(Salle.class, 1L, LockModeType.PESSIMISTIC_WRITE);

TP 7 • Caches & Haute Performance 📁 Repositoire : TP7-Second-Level-Cache-N1-Problem

Cache de Second Niveau (L2) & Le Piège N+1

Ehcache, mise en cache des requêtes, L1 vs L2 et EntityGraph

🛑 Le Problème Initial (Pourquoi ce TP existe) :

Sans cache L2, si 1000 utilisateurs consultent la liste des salles de réunion, Hibernate exécute 1000 fois les mêmes requêtes SQL vers la base, gaspillant du CPU et de la bande passante réseau. De plus, charger des associations en LAZY hors transaction déclenche l'exception classique LazyInitializationException.

✅ La Solution & Innovation Apportée :

Configuration du cache L2 avec Ehcache (hibernate.cache.use_second_level_cache=true), annotation @Cacheable sur les entités de référence peu modifiées, et utilisation de JOIN FETCH ou @EntityGraph pour initialiser les graphes d'objets.

🔬 Ce qu'il faut absolument connaître dans ce TP :

Architecture L1 Cache vs L2 Cache

Cache L1 : Lié à UN SEUL EntityManager. Durée de vie = la transaction. Non partagé, non désactivable. Cache L2 : Lié à l'EntityManagerFactory (toute l'application). Partagé entre tous les threads et sessions. Survit à la fermeture des EntityManagers.

<!-- Configuration dans persistence.xml -->
<property name="hibernate.cache.use_second_level_cache" value="true"/>
<property name="hibernate.cache.region.factory_class" 
          value="org.hibernate.cache.jcache.JCacheRegionFactory"/>
<property name="javax.persistence.sharedCache.mode" value="ENABLE_SELECTIVE"/>

Activer le Cache sur une Entité

On utilise @Cacheable (standard JPA) et @Cache (spécifique Hibernate pour définir la stratégie de concurrence, ex: READ_WRITE ou READ_ONLY).

@Entity
@Cacheable
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Salle {
    @Id @GeneratedValue
    private Long id;
    private String nom;
}

L'Exception Mythique : LazyInitializationException

Survient lorsqu'on tente d'accéder à une collection ou association annotée FetchType.LAZY alors que l'EntityManager qui a chargé l'entité parente a déjà été FERMÉ (em.close()). Le proxy Hibernate ne peut plus contacter la base !

// Erreur typique :
EntityManager em = emf.createEntityManager();
Salle s = em.find(Salle.class, 1L);
em.close(); // Fermeture de la session !
System.out.println(s.getEquipements().size()); // BOOM : LazyInitializationException !

Algorithme Mathématique Anti-Chevauchement de Créneaux

Deux créneaux [debutA, finA] et [debutB, finB] se chevauchent si et seulement si : debutA < finB ET finA > debutB. Cette condition est traduite directement en requête JPQL ultra-performante.

String jpql = "SELECT COUNT(r) FROM Reservation r " +
              "WHERE r.salle.id = :salleId " +
              "AND r.dateDebut < :fin " +
              "AND r.dateFin > :debut";
Long conflits = em.createQuery(jpql, Long.class)
    .setParameter("salleId", salleId)
    .setParameter("debut", nouveauDebut)
    .setParameter("fin", nouveauFin)
    .getSingleResult();
if (conflits > 0) {
    throw new ReservationConflictException("La salle est déjà réservée sur ce créneau !");
}

Service Pattern & Démarcation Transactionnelle

La couche Service isole le code métier de la persistance. C'est elle qui gère les transactions et garantit la cohérence ACID.

public class ReservationService {
    public Reservation reserverSalle(Long salleId, Long userId, LocalDateTime debut, LocalDateTime fin) {
        EntityManager em = HibernateUtil.getEntityManager();
        EntityTransaction tx = em.getTransaction();
        try {
            tx.begin();
            // 1. Vérification conflit horaire
            verifierDisponibilite(em, salleId, debut, fin);
            // 2. Création et association
            Salle salle = em.find(Salle.class, salleId);
            Utilisateur user = em.find(Utilisateur.class, userId);
            Reservation res = new Reservation(salle, user, debut, fin);
            em.persist(res);
            tx.commit();
            return res;
        } catch (Exception e) {
            if (tx.isActive()) tx.rollback();
            throw e;
        } finally {
            em.close();
        }
    }
}

Questions Pièges Générales d'Interrogation Orale

Les questions transversales que les examinateurs adorent poser pour départager les étudiants.

Piège Oral #1 Proxies & L1

Quelle est la différence entre EntityManager.find() et EntityManager.getReference() ?

find() exécute immédiatement un SELECT SQL et retourne l'entité peuplée ou null. getReference() ne fait aucune requête SQL immédiate : il renvoie un Proxy CGLIB/ByteBuddy avec juste l'ID. La requête SELECT n'est déclenchée que lorsque l'on appelle un getter sur un autre champ. Si l'ID n'existe pas en base, une EntityNotFoundException survient lors de l'accès.

Piège Oral #2 Interne Hibernate

Qu'est-ce qu'un Proxy Hibernate ?

C'est une classe générée dynamiquement au runtime par Hibernate qui hérite de votre entité. Elle intercepte les appels de méthodes. Tant que les données ne sont pas nécessaires, elle retarde l'appel SQL (Lazy Loading). Dès qu'un champ est sollicité, le proxy charge les données depuis la base.

Piège Oral #3 Spécification JPA

Pourquoi le constructeur par défaut (sans arguments) est-il OBLIGATOIRE sur toute entité JPA ?

Parce qu'Hibernate utilise la réflexion Java (Class.getDeclaredConstructor().newInstance()) pour instancier les objets lorsqu'il lit les lignes d'un ResultSet JDBC. Sans constructeur sans argument (qui peut être public ou protected), Hibernate ne peut pas instancier l'entité et lance une InstantiationException.

Piège Oral #4 Transactions

Quelle est la différence entre em.flush() et em.getTransaction().commit() ?

em.flush() synchronise le contexte de persistance avec la base en envoyant immédiatement toutes les requêtes SQL (INSERT, UPDATE, DELETE) en attente, mais ne valide pas la transaction. em.getTransaction().commit() effectue d'abord un flush() implicite, puis envoie l'instruction COMMIT SQL physique pour rendre les changements définitifs.

Piège Oral #5 Règles Java

Peut-on mettre des champs statiques (static) ou finaux (final) sur une entité JPA ?

Les champs static ne sont jamais persistés (ils appartiennent à la classe et non à l'instance). Les champs et méthodes ne doivent pas être final, car cela empêcherait Hibernate de générer des proxies par sous-classement dynamique.

🏆 Les 3 Règles d'Or pour l'Interrogation Orale devant le Professeur

1. La Règle des 3 Temps

Ne donnez jamais une réponse en un mot. Structurez toujours ainsi : 1. Définition technique (ex: Contexte de persistance), 2. Ce qui se passe en base SQL (requêtes, transactions), 3. L'impact dans le TP.

2. Les Mots-Clés Magiques

Employez les termes exacts qui prouvent votre niveau : "Dirty Checking", "First-Level Cache", "Proxy CGLIB", "Cascade de suppression", "Isolation ACID", "Pagination côté serveur".

3. Si vous avez un bug en direct

Ne paniquez jamais. Regardez la console et lisez la cause racine (Caused by). 90% des bugs de TP sont : oubli de transaction (RESOURCE_LOCAL), LazyInitializationException (session fermée) ou contrainte de clé étrangère.
